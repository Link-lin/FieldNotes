# Atlas v1 — dashboard globe and destination location

**Status:** First-release design, subordinate to [`PRD.md`](../../PRD.md) ATLAS-1–7 and the [technical design](technical-design.md).  
**Design reference:** [Travel Planner Figma file](https://www.figma.com/design/IIIxFv7pRJzgJOHcyG5Y6D/Travel-Planner-%E2%80%94-Product-UI-UX?node-id=3-3), “Global Atlas — World View”. The Figma screens illustrate layout and color; this document and the PRD govern behavior and data.

## Scope and product meaning

The globe is a way to browse trips, with **one approximate destination point per trip**. It does not show itinerary stops, actual travel, flight paths, live location, directions, or a visited-country total. Itinerary stops appear only on the schematic day map described in [Trip page v1](trip-page-v1.md). A trip may have no point and must still be visible and openable in the dashboard list. The owner can correct or clear a point. A viewer can only read the points for trips they can already read.

The first-release dashboard has **All**, **Upcoming**, **Ongoing**, and **Past** filters. One server-authorized `DashboardDTO` feeds both the list and the globe. Filtering is client-side over that response; the date status comes from the server's trip-time-zone calculation. Selecting a marker highlights its list card and offers **Open trip**. Selecting a list card highlights and rotates/focuses the matching marker if one exists. Opening a trip works from either view. The list is the complete, keyboard-operable route; do not make globe drag or hover the only way to reach a trip.

## Location data and creation rules

Add nullable `atlas_latitude NUMERIC(8,5)`, `atlas_longitude NUMERIC(8,5)`, and `atlas_source TEXT` (`catalog` or `owner`) to `trips`. All three are either present or absent; check latitude `[-90,90]` and longitude `[-180,180]`. The point is independent of the human-readable `destination`. It is returned as `{ latitude: number, longitude: number, source: "catalog" | "owner" } | null` in `TripSummaryDTO`; the API never returns a marker for an unauthorized trip. Coordinates are ordinary approximate map coordinates, not personal location telemetry. Do not call the browser geolocation API.

Bundle a versioned, reduced search index derived from [Natural Earth populated places](https://www.naturalearthdata.com/downloads/10m-cultural-vectors/10m-populated-places/) and country names/label points, plus simplified [Natural Earth](https://www.naturalearthdata.com/about/terms-of-use/) world geometry. Record source version and generation command with the assets. Natural Earth describes its map data as public domain. Keep the index on the app server and serve globe assets from the same app origin; do not call a public geocoder, map tile service, or CDN from the dashboard. This keeps globe display independent of provider keys and does not reveal trip destinations to a map service.

On manual trip creation and confirmed import, normalize the destination for catalog matching: Unicode normalization, trim, case folding, and collapsed whitespace. Support `City, Country` and exact country names; a city-only name matches automatically only when unique across the catalog. Require an exact, unambiguous match to a catalog entry before storing its representative point. Do not infer from itinerary item locations, airport codes, AI-supplied prose, or partial/fuzzy name matches. A city, region, cruise, or multi-stop trip that does not match remains unlocated. The same matching function runs inside trip creation/import before the trip transaction commits; a catalog error should leave the point null without failing an otherwise valid trip. Record only a sanitized error code, never the destination.

Owner correction uses an authenticated, bounded `GET /api/atlas/places?q=...` search over the local index: query length 2–160, at most ten matches, each with a label, catalog ID, latitude and longitude. It does not query an external service or read trip data. The owner may choose a result or click the globe to choose a point. A chosen point is saved through the trip `PATCH` with `atlasLocation: { latitude, longitude }` and `expectedVersion`; the server validates finite decimal coordinates to five fractional places and assigns `atlas_source='owner'`. `atlasLocation: null` explicitly clears it. An omitted `atlasLocation` means no explicit location edit. Viewers get no location mutation control or write access. A manual point uses the trip destination as its marker label; the UI calls it approximate.

When the destination text changes, an existing `catalog` point is rematched and replaced or cleared. An `owner` point is preserved; before save, the editor warns that the destination and point may no longer agree and lets the owner keep, replace, or clear it. If the `PATCH` explicitly includes `atlasLocation`, that action takes precedence over automatic rematching. The same trip version check protects concurrent destination/point edits. A stale update returns 409 and the form preserves the user's selection for reapply.

## Rendering and states

Use a client-only, lazy-loaded globe component. As implemented, it is a canvas orthographic globe drawn with `d3-geo` and `world-atlas` land-110m and countries-110m (no WebGL; see technical design section 20). It shows country borders and names; more names appear as you zoom in, and names never cover a trip marker or its label. Render a lightweight bundled world layer and points from the authorized DTO. Do not render the globe during server-side HTML generation. Avoid continuous rotation. One intro rotation of under two seconds on first load, a pulse on upcoming markers, and a slow dashed ring are decorative and must be skipped under reduced motion. Zoom works with the mouse wheel or pinch as well as explicit zoom and reset controls, and dragging turns the globe. Zoom and drag ease out like a map app: zoom glides to its new level after the wheel stops, and a quick flick keeps the globe turning briefly before it slows to a stop. Under reduced motion both happen immediately. Looping motion stops within 10 seconds of the last interaction. Marker status uses shape as well as color (circle upcoming, diamond ongoing, ring past). At a narrow viewport, put the trip list before or adjacent to the globe and keep its controls reachable without canvas interaction.

The authenticated dashboard list renders first. Show a globe loading placeholder while its code/assets load. If the canvas is unavailable, a render error occurs, or map assets fail, replace the canvas with a short explanation and keep the full list/filters/actions. An empty dashboard has a create-trip action. When no trips have points, show the globe's empty state and the complete trip list; owners see **Set globe location** on unlocated cards. Multiple trips may share coordinates: selecting the point must expose all matching trips in a small accessible list rather than hiding all but one. Marker and list state must update after create, edit, delete, permission revoke, and filter changes. No location or title is written to browser storage or analytics.

The Figma examples may contain illustrative trip counts, country counts, or budget figures. Implementation must derive any displayed number from supported data. Omit country and annual-spend metrics in v1; the latter has no paid-amount model. The visual direction is now the warm paper-and-ink palette defined in [Trip page v1](trip-page-v1.md#visual-direction) (cream paper, brown ink, vermilion accents, pale-blue ocean), which replaces the earlier navy and lake-blue treatment; the Figma screens need updating to match. Green stays rejected as a brand or surface color. The forest accent is used only for the Booked state and under-budget bars and needs the owner's confirmation. Use shared tokens/components when the app is scaffolded; Figma pixels do not override accessibility, responsive behavior, or PRD scope.

## Validation and operations

- Check catalog generation output and licensing notes into the repository with a deterministic source version; keep runtime free of a geocoder key or external map availability dependency.
- Test exact/ambiguous/unmatched matching, owner correction/clear, destination edit rules, coordinate bounds, and stale-version conflict.
- Test owner/viewer/anonymous dashboard and search/write permissions, including immediate revocation. A revoked trip marker must disappear on the next protected fetch.
- Test list/globe filter synchronization, shared-coordinate selection, no-point trips, WebGL/asset failure, reduced motion, keyboard navigation, and small screens.
- Load-test only the realistic personal-data bound (the existing 250-item trip cap does not bound trip count). Keep markers and the list responsive with dozens of trips; measure before adding clustering or pagination.
- Do not log destination search text or coordinates. Serve world assets from the app origin and confirm no browser request to third-party tile/geocoding endpoints in the dashboard.

## Tradeoffs

Bundled place matching avoids another account, API key, cost, and privacy boundary. It cannot resolve every locality or multi-stop description. The explicit point editor and list fallback handle those cases. A WebGL globe adds bundle size and a graphics failure mode; lazy loading and a complete semantic list contain that cost. The product should validate whether people actually use the globe before adding route lines, per-item geocoding, country totals, or further map infrastructure.
